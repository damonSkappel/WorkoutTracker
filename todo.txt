------ FUTURE PLANS ------
Bigger features, not blocking anything. No particular order.

F1. Verify email addresses by sending a code.
    Signup currently accepts any well-formed address without proving it exists.
    Format validation only catches typos - it cannot tell you the mailbox is real
    or that the person signing up owns it.
    Roughly what this needs:
      - an email_verifications table: user_id, code_hash, expires_at, consumed_at
        (hash the code, same reasoning as refresh tokens - a db leak should not
        hand out working codes)
      - a 6-digit code, short expiry (10-15 min), rate limited, single use
      - POST /auth/send-verification and POST /auth/verify-email
      - a `verified_at` column on users, and a decision: can unverified users
        use the app, or only look at a "check your inbox" screen? Letting them
        in and nagging is friendlier than locking them out.
      - an actual mail sender. This is the part that costs money/setup:
        Resend, Postmark, SES. Needs a real sending domain, not localhost.
    Prerequisite for a "forgot password" flow, which is the real reason a
    verified address matters - without one, a lost password means a lost account.

F2. Forgot password / password reset. Depends on F1.

F3. Reorder exercises within a template.
    order_index is a real, distinct position per exercise now (was hardcoded to 1
    for everything), so the data side is already in place - this is a UI job plus
    one endpoint.
    Roughly what this needs:
      - a drag handle on each row of the template screen. react-native-draggable
        -flatlist is the usual pick; RN has no built-in reorderable list.
      - PUT /api/templates/:id/exercises/order taking the exercise ids in their
        new order, rewriting order_index 1..N in a single transaction so a failure
        part way through cannot leave two exercises sharing a position.
      - ownership checked the same way as the other exercise endpoints, and a
        check that the ids sent are exactly the ids in that template.
    Worth noting: reordering a template does NOT change workouts already done.
    Sets point at template_exercise_id, and past sessions keep whatever order
    they were performed in, which is correct - history should not rewrite itself.

F5. Replace the explicit `any`s with real types.
    strict: true is on, but it does not complain about `any` you wrote on purpose,
    and the screens are full of them - useState<any[]> for templates/sets/exercises,
    (item: any) in every renderItem, err: any in every catch.
    The win: define the API response shapes once (Template, TemplateExercise,
    WorkoutSession, WorkoutSet) and the compiler starts catching field-name typos
    and null access in the screens, which is where the real bugs have been.
    Reasonable order: types file -> utils/api.ts generics -> one screen at a time.

F4. Change password while logged in. Needs the current password re-entered, and
    should revoke all other refresh tokens so a password change actually kicks
    out anyone else who was signed in.
